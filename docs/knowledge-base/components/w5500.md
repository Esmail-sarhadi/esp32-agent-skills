# W5500 Hardware and Driver Dossier

## Device boundary

W5500 is a hardwired TCP/IP Ethernet controller with an SPI host interface and multiple hardware sockets. It is not an RMII PHY. The ESP32 application typically communicates with the controller over SPI and uses the library/driver's socket abstraction. Do not mix its offloaded socket model with native ESP-IDF Ethernet/lwIP APIs unless the selected integration explicitly supports that combination.

## Schematic review

Verify the exact module schematic for regulator, reset circuit, clock source, magnetics, RJ45 connector, LEDs and logic-level compatibility. Record SPI SCK/MOSI/MISO/CS, reset and interrupt pins. Check CS polarity and ensure no other device drives MISO while CS is inactive. Validate reset timing and power stability during link negotiation.

## Driver and resources

The chip exposes a finite hardware socket pool and configurable per-socket TX/RX memory allocation. Track socket ownership and close sockets on every error path. Bound DNS, connect, read and write timeouts. Handle link-down, DHCP failure, peer close and reconnect without leaking socket handles.

## Network bring-up sequence

1. Verify SPI communication and chip/version identification.
2. Read link state and confirm PHY negotiation.
3. Obtain DHCP or validate static IP, gateway and subnet.
4. Test DNS separately.
5. Test a minimal TCP client before adding MQTT, WebSocket or Matter.
6. Exercise cable removal, router restart and long power-off recovery.

## Known diagnostic trap

A device receiving a DHCP lease does not prove the application socket path is healthy. Isolate link, DHCP, DNS, TCP connect, socket lifecycle and higher-level protocol. Community crash reports involving W5500 and network stacks are not proof of a universal W5500 silicon defect.

## Verification

| Test | Evidence |
|---|---|
| Cable absent at boot | No blocking boot; link state reported |
| Cable inserted later | Link and DHCP recover |
| DHCP unavailable | Bounded retry and visible status |
| Peer closes socket | Socket resource reclaimed |
| Repeated reconnect | No socket exhaustion or monotonic heap loss |
| Long power-off | Application identity and session recover |
